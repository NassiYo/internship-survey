# Работа через pull request

Все изменения проекта оформляем в отдельных ветках и PR. PR не сливаются автоматически.

1. Изменить спецификацию, если меняется поведение.
2. Уточнить технический план и задачи.
3. Реализовать изменение в отдельной ветке.
4. Проверить критерии приёмки, тесты, типы и сборку.
5. Открыть PR с описанием результата и выполненных проверок.

Начальные PR: #1 — спецификация и план, #2 — приложение (основано на ветке #1). После слияния #1 перенести базу #2 на main.

Ключи, .env, .dev.vars, локальные базы и реальные ответы не коммитить. Настройки доступа хранятся в runtime-переменных Sites. Публичный GitHub-репозиторий содержит исходники, но не предоставляет доступ к собранным анкетам.

GitHub — место просмотра и согласования кода. Sites — место публикации исполняемой версии; у него отдельное служебное хранилище исходников. В текущей версии GitHub Actions проверяет PR, но не развёртывает сайт автоматически.
